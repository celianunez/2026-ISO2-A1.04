# Decisions log – SESCAM Radiodiagnostics (ISO II – 3A1.04)

This file records the key decisions of the project.

**How to use it:**

- **Adding a decision:** give it the next ID, the date, the decision, the reason and its status.
- **Status values:**
  - *Proposed*: not agreed yet.
  - *Accepted*: agreed by the team, with the meeting date.
  - *Replaced by D-XX*: superseded by a later decision.
- **Changing a decision:** never delete an accepted one; add a new decision that replaces it.

## Decisions

| ID | Date | Decision | Reason | Status |
|----|------|----------|--------|--------|
| D-01 | 04/11/2026 | **Modular monolith**: one Spring Boot application (`radio-app`) made of independent modules. | Team size and timeline. Simple deployment. Microservices would add too much overhead. | Accepted (team, 13/11/2026) |
| D-02 | 04/11/2026 | **One Maven submodule per component (17)** plus `radio-app`, which only starts the application. There is no central `radio-api` module. | The assignment asks for one submodule per component. See the list in `docs/architecture/architecture-proposal.md` (section 3). | Accepted (team, 13/11/2026) |
| D-03 | 04/11/2026 | **Each module has its own `api` package**, with its public interfaces, DTOs and REST controllers. Every interface belongs to the module of the component that provides it. Other modules only use that `api`. | Low coupling: each module can be developed and tested separately. | Accepted (team, 13/11/2026) |
| D-04 | 04/11/2026 | **Stack: Java 17, Maven, Spring Boot 3.5.16, JUnit 5.** | Spring Boot 3.5.16 is the stable line with Java 17 and JUnit 5. Spring Boot 4 brings JUnit 6 and renamed starters, which is not worth it with our deadlines. | Accepted (team, 13/11/2026) |
| D-05 | 04/11/2026 | **The dependencies between modules must have no cycles.** A module only depends on modules of a lower level (table in section 5 of the architecture document). | Avoids compilation and design problems. It also gives a build order. | Accepted (team, 13/11/2026) |
| D-06 | 04/11/2026 | **Each module owns its own tables and repositories.** No module reads or writes another module's tables. Only exception: `radio-metrics` may run read-only queries for statistics. | Modules stay independent. The metrics need data from several modules (HU-11, HU-16, HU-22). | Accepted (team, 13/11/2026) |
| D-07 | 04/11/2026 | **Only `radio-request` changes the status of a request.** The other modules call `IRequestService` (`markScheduled`, `markPerformed`, `markReported`…). | A single source of truth for the request lifecycle (HU-08). | Accepted (team, 13/11/2026) |
| D-08 | 04/11/2026 | **External systems (SSO, HCE/admission, RIS/PACS) go through adapter modules with a simulator.** Integration failures are recorded and never block the rest of the system. | Required by HU-20, HU-21, HU-24 (integration-failure flow of CU-20, CU-21, CU-24; CU-42 before D-23). We can develop and test without the real systems. | Accepted (team, 13/11/2026) |
| D-09 | 04/11/2026 | **Security with Spring Security, configured in `radio-auth`.** Permissions are checked on the server, not only in the UI. The other modules use the roles and the current user from Spring Security. | HU-18. Modules do not need a dependency on `radio-auth`, which avoids cycles. | Accepted (team, 13/11/2026) |
| D-10 | 04/11/2026 | **Audit in `radio-audit`, append-only.** Every access to clinical data is recorded, and records cannot be edited or deleted. | HU-19, CU-19-S (CU-38 before D-23). GDPR: health data. | Accepted (team, 13/11/2026) |
| D-11 | 04/11/2026 | **A single metrics module (`radio-metrics`)** for HU-11, HU-16 and HU-22. | Suggested in the user stories Excel. The same queries are not repeated three times. | Accepted (team, 13/11/2026) |
| D-12 | 04/11/2026 | **Modules communicate through direct calls to the interfaces.** There is no event bus for now. Images are not stored, only retrieved from the PACS. | Simpler, and it matches the «include» relations of the use cases. HU-24 asks for images "without duplicating them". | Accepted (team, 13/11/2026) |
| D-13 | 05/11/2026 | **Module names follow the architecture proposal v0.3**, in singular: `radio-auth`, `radio-configuration`, `radio-catalogue`, `radio-patient`, `radio-request`, `radio-scheduling`, `radio-execution`, `radio-report`, `radio-image`, `radio-feedback`, `radio-metrics`, `radio-notification`, `radio-audit`, `radio-jobs`, `radio-sso-adapter`, `radio-hce-adapter`, `radio-pacs-adapter`, plus `radio-app`. | The architecture proposal renumbers the components as C1–C17 and splits the integration module into three adapter modules, one per external system, each with its simulator. Having one name per module in the POMs, the diagrams and the documents avoids the mismatch we had in v0.2. | Accepted (team, 13/11/2026) |
| D-14 | 10/11/2026 | **Module boundaries and cycles are checked by the build**: an ArchUnit test (a class of module X may only use the `api` package of another module Y; no cycles between modules) and `maven-enforcer` (Java ≥ 17, Maven ≥ 3.8). It runs inside `mvn -B verify`, so the CI enforces it on every PR. | D-05 and D-03 were rules only "by convention"; with code generated by an AI agent a rule that is not executed is not a rule. Closes the tool choice left open in `sqa-plan.md` §9. | Accepted (team, 13/11/2026) |
| D-15 | 10/11/2026 | **One version for the whole repository until `1.0.0`, and one identified configuration per iteration**: every iteration ends with `CFG-0N`, an annotated tag `cfg-iter0N` on `develop` with a version without `SNAPSHOT`. The configuration is the tag plus the list of modules that exist and that changed (map in `scm-plan.md` §3.1.4). | Resolves R-12 of `development-workflow.md`. All modules are deployed together (D-01), so per-module versions would multiply the release work by 18 without adding information; the CFG map keeps the per-module view. | Accepted (team, 13/11/2026) |
| D-16 | 10/11/2026 | **Milestone configurations are labelled with SemVer pre-releases**: CFG-02 `0.3.0-alpha.1` (alpha 1), CFG-03 `0.4.0-alpha.2` (alpha 2 = architecture baseline), CFG-06 `0.7.0-beta.1` (beta), CFG-07 `1.0.0-rc.1` (release candidate) and `1.0.0` (final). A label is given when its **exit criteria are met, not when the date arrives**; otherwise the label is delayed and the reason is written in the minutes. | The assignment asks to anticipate alpha, beta and final versions on top of the minimum configurations. Criteria make the label verifiable. | Accepted (team, 13/11/2026) |
| D-17 | 10/11/2026 | **Quality gates grow with each release** (coverage, traceability, adapter failure tests, defects, restore rehearsal), table in `sqa-plan.md` §5.2.1. The JaCoCo `check` thresholds are the properties `coverage.line.minimum` and `coverage.branch.minimum` of the parent POM, raised on each `release/*` branch. | A single 70 % target from day one is either ignored (too strict early) or too weak at the end. | Accepted (team, 13/11/2026) |
| D-18 | 10/11/2026 | **Environments `dev` → `ci` → `test` → `alpha` → `beta` → `demo`, and rollback = check out a `cfg-iter0N` tag, rebuild with `mvn -B clean verify`, redeploy that jar and restore the database copy of that configuration.** Every release has a `DEPLOY-<version>.md` with the exact module list. | Every configuration must be deployable and recoverable, not only buildable. Depends on P-04 (database). | Accepted (team, 13/11/2026) |
| D-19 | 10/11/2026 | **`radio-app` is created in Iteration 1**, with the first modules, and grows every iteration. | Without the composition root no alpha can be run end to end. Replaces the wiki draft that created it in Transition. | Accepted (team, 13/11/2026) |
| D-20 | 10/11/2026 | **Packages inside a module: `api`, `domain`, `application`, `infrastructure`** (architecture proposal v0.3 §2). Only `api` may be used by other modules (D-03, checked by D-14). The `internal` package of the configuration-test modules `module-a`/`module-b` is equivalent to `domain` + `application` + `infrastructure`. | The wiki draft used `api/domain/internal/app`; one layout everywhere. | Accepted (team, 13/11/2026) |
| D-21 | 10/11/2026 | **8 iterations of one week, grouped by blocks of user stories** (`project-plan.md` §5). Replaces the draft with 28 iterations (one per story) that remained on some wiki pages. Each use case is still realised in one and only one iteration. | Justified in `project-plan.md` §5.2 (capacity, overhead, integration). | Accepted (team, 13/11/2026). Dates replaced by D-25 when D-25 is accepted; the blocks and their order do not change |
| D-22 | 13/11/2026 | **The project plan, the SCM plan and the SQA plan are approved as v1.0** and submitted to Moodle as Theoretical Assignment 1 (`ISOFT2-26-27-ET.01-3A1.04.zip`), as three separate PDF files generated from `docs/plans/`. The PDFs link every referenced file to this repository on GitHub. Later changes to the plans start a new version (v1.1, …) recorded in their history table. | The assignment asks for the three plans by 13 November. Keeping the repository files at the same version as the submitted PDFs makes the delivery traceable. | Accepted (team, 13/11/2026) |
| D-23 | 23/11/2026 | **One use case per functional requirement, with the same number: HU-nn = FR-nn = CU-nn (26 use cases).** The 45 use cases of v1 become flows of their story's use case (for example *Cancel appointment* is a flow of CU-01). Each FR comes from one bullet of the assignment; four bullets were split into several stories (Adm·2 → HU-13, HU-26; Ph·4 → HU-09, HU-25; Sys·1 → HU-17, HU-23; Sys·4 → HU-20, HU-21, HU-24). | The assignment recommends 1 FR : 1 UC and 1 UC : 1 iteration. With 45 use cases the numbers of FR and CU did not match (FR-20 ↔ CU-40) and traceability was hard to follow. Mapping in wiki *02) Use Cases*, section *Former use cases*. | Accepted (team, 23/11/2026) |
| D-24 | 23/11/2026 | **Every use case has a client part `CU-nn-C` and a server part `CU-nn-S`**, joined in the diagrams by the system actors *Client* and *Server*. Each part has its own sub-issue (issue templates *Use case* and *Use case part*), branch and tests. Client = UI page in `radio-app` and its REST call; server = `web` + `api` + `application` + `domain` of the module. | The system is client-server (assignment, section 1). Splitting the parts makes clear what the agent implements on each side, lets two people work in parallel on one use case, and keeps the business rules on the server (HU-18). | Accepted (team, 23/11/2026) |

| D-25 | 24/11/2026 | **Compressed calendar.** The 8 iterations, their blocks and their use cases stay the same, but iterations 1–7 last 2–3 days: foundation 24–25/11, It 1 25–28/11 (CFG-01 `0.2.0`), It 2 29/11–01/12 (Alpha 1), It 3 02–04/12 (Alpha 2), It 4 05–07/12 (CFG-04), It 5 08–09/12 (CFG-05), It 6 10–12/12 (Beta), It 7 13–14/12 (RC → `1.0.0` on 15/12). Every iteration ends with a code freeze at 12:00 of its last day. Tables in `project-plan.md` §5.1 and `scm-plan.md` §3.1.4. | On 24/11 no product code existed and the plan of D-21 had iterations 1–3 finished (about three weeks of slippage). The delivery date is fixed (project plan §8), so the iterations are shortened and the seven members work in parallel on different modules (D-29). Root causes and recovery: wiki *10) Project History*, post-mortem. If an iteration does not pass its gate, the scope is cut (block 4 first), never the gate (D-16, D-17). | Proposed (24/11/2026) |
| D-26 | 24/11/2026 | **Contracts first.** Every iteration starts with one pull request by the architect with the `api` interfaces, DTOs and `api` exceptions of its modules (no implementation), reviewed by the quality lead. The owners then implement in parallel against those interfaces and mock the ones not merged yet. A change to a merged contract is a breaking change (`feat(x)!:` and a decision here). | With 2–3-day iterations nobody can wait for the module below to be finished. Stable contracts let several people work at the same time and make the contract tests of the SQA plan possible from day one. | Proposed (24/11/2026) |
| D-27 | 24/11/2026 | **The pending points P-01 to P-13 are resolved with the proposals written in the table below**, with one change: **P-04 uses H2 for every environment** (in memory for `dev` and `test`, a file for `demo`), instead of PostgreSQL or MySQL for the demo. In short: HCE is the source of truth when the patient exists there (P-01) · simulated OpenID Connect (P-02) · configuration = global parameters, catalogue = test-type attributes (P-03) · static HTML/JS client in `radio-app` (P-05) · in-app inbox + email stub (P-06) · 4 roles (P-07) · waiting list stays in `radio-scheduling` (P-08) · `radio-common` with package `es.uclm.sescam.common.api` (P-09) · controllers in a `web` package (P-10) · `I` prefix (P-11) · `radio-catalogue` depends on `radio-audit` (P-12) · metrics by read-only queries (P-13). | The code starts on 25/11 and every point affects it. The proposals were written and reviewed on 04–05/11 and nobody objected. H2 file for the demo avoids installing a database server on every machine and is enough for a prototype; the restore rehearsal of D-18 copies the H2 file. Putting `radio-common` in an `api` package keeps the ArchUnit rule of D-14 without exceptions. | Proposed (24/11/2026) |
| D-28 | 24/11/2026 | **`CONTEXT.md` and `AGENTS.md` at the repository root are the descriptors for the AI agents** of every member: architecture rules, module owners, Definition of Done, what an agent may and may not change, and how it works (signatures first, tests designed by the human, `mvn -B verify` at the end). | The assignment asks to bind the Unified Process artefacts to Spec-Driven Development descriptors (`CONTEXT.md`, `PLAN.md`) with the human in the loop. Seven agents without common rules would produce seven styles. | Proposed (24/11/2026) |
